# ePVS 接口用例具体修改建议

日期：2026-10-27。范围：riqor-apitest/cases/epvs。本轮仅生成建议，不修改用例、框架或既有执行证据，不请求共享环境。

本轮读取到 108 条 @case。AUTO-002（Tukey）和 AUTO-040（四象限）已从当前 Python 用例中移除，plan.yaml 保留缺口；部分断言、依据类型和恢复检查已经调整。本文按这个版本提出后续修改，不沿用上一轮“110 条全部仍在”的描述。工作区有并行修改，实施前须再次核对对应文件。

## 1. 修改时遵循的判定

- 状态码、类型、必填字段、白名单等断言可以保留。先定位支持该期望的需求、接口约定或缺陷修复约定，再决定是否确认依据；不要求每条都查询数据库。
- 明确写出每条用例的验证目标。接口可读、字段自洽、参数等价、业务结果正确是不同目标。
- 计算正确性与数据筛选正确性需要独立的预期。数据可来自受控环境中提前准备的记录，或同一截止点的只读明细；静态文件只有对应真实服务的数据时才可作为接口期望。
- 用原始明细或受控数据清单确认前提。预期有数据而接口返回空，应暴露产品问题，不能根据被测返回为空自行跳过。
- 纯空结果响应也是独立的合法场景；验证有数据时的字段、过滤或计算时，应单独准备非空场景。
- 已知产品缺陷应保留正确预期，未修复就失败。只为观察现状而保留的断言应单独标明目的。
- 本地模拟响应只能证明用例有没有检测能力，不能证明真实服务符合需求。

## 4. 当前无 API 判据的目标怎么保留

### Tukey：禅道2847 / 2848，原 AUTO-002

当前移除空实现并在计划保留缺口是合理的过渡处理，但不代表过滤已验收。

补测路线：在隔离测试环境预置与真实查询路径匹配的动作级事件，或获取一致截止点的只读原始明细。把参考计算放在项目自己的普通 Python 模块里，冻结分位数算法、栅栏系数、端点包含规则、去重规则与时间过滤规则。

可设计以下数据组（数值为建议数据，不是当前环境事实）：

- 普通组：[10,11,12,13] 重复 5 次，再加入 1 和 100。独立参考函数先确认栅栏和保留集合；期望同时检查保留数量、统计值与明细成员，若接口并不返回明细，则明细目标须放在实际提供它的接口或集成层验证。
- IQR=0：20 个 10，再加一个 100；按已确认规则核对等值样本是否保留、异常值是否排除。
- 小样本、空集、栅栏恰好相等、重复事件、窗口外事件，各自独立成场景。

“短周期 average 是否被忽略”是参数语义目标，“Tukey 是否正确排除”是算法目标，应分开。前者尚未确认时不能改写成另一个 p50 拒绝断言就声明覆盖完成。

### 四象限：禅道2670，原 AUTO-040

接口若只提供 ratio/trend，API 测试可验证这两个输入的计算与类型；分类显示移到 Web 测试。Web 使用受控响应覆盖四象限及 ratio=1、trend=0 等边界，边界归属由明确需求决定。不要通过测试代码自己分类再验证自己的分支互斥。

保留已退役的 AUTO 身份记录，后续新增目标不复用旧 ID。若恢复原目标，沿用原身份前须核对历史语义。

## 5. 所有写用例的共同改法

1. 数据优先使用本轮创建的隔离对象；必须使用固定共享对象时，需要环境执行授权、排他运行、精确基线和恢复路径。
2. 基线与预期分开：基线服务于恢复和不变字段比较；本轮唯一名称、创建输入及确认过的规则服务于验证预期。读取到什么都认可，不能证明创建字段正确。
3. 创建后立刻登记清理，并覆盖 fixture setup 中途异常的情况；用 try/finally 或 ExitStack 管理已经成功创建的每个对象。
4. 清理检查状态码与最终回读。任务/车型 fixture 目前仍有仅发送删除请求而未确认回收的路径。
5. 如果写接口有异步契约，轮询完成状态与目标最终值，设置总超时；记录每次回读。不要用固定 sleep 代替完成判据，也不要重试原写请求掩盖非幂等问题。
6. 失败状态归因须有环境依据：401/403 也可能是鉴权回归，503 也可能是产品可用性故障，不能仅凭状态码自动认定可跳过。
7. 非法请求也是可能有副作用的写请求。拒绝状态检查失败后仍应回读和清理，不能因“预期会被拒绝”就没有恢复。

## 6. 依据、证据和计划同步修改

- 当前许多 _spec 已使用 measured，这有助于避免把现象冒充规范。下一步逐条寻找已确认来源，而不是为了恢复绿色批量改回 schema(confirmed=True)。没有 OpenAPI 不代表不能有接口契约；可以编写经核对的本地接口约定，明确版本和条目，但内容必须有实际支持。
- 已确认正确行为应关联具体需求或缺陷修复约定；例如“返回 4xx”不能自行变成“必须 422”。
- 历史观察作为回归基线时，记录冻结运行/证据包、服务版本、输入与数据条件、审核采纳信息，固定预期，失败时不自动覆盖基线。不能只在字符串里写“2026-10-27 实测”。框架支持字段以实施时已完成的契约为准。
- 每条断言增加实际字段位置 source 和参与比较的请求 refs；跨两次请求比较时保存双方 request_id。框架客户端已提供 response.request_id，无需在用例里发明请求编号。
- 每个 required_assertions.text 写出行为和条件。类似“由 AUTO-xxx 覆盖”的文本替换为可独立审阅的验收条件；AUTO 关系由执行结果映射。
- 参数组合逐项独立收集，适合的地方用 pytest.mark.parametrize。每个组合的前提、执行结果、断言和证据独立；例如一个非法参数失败，不应导致其余值根本没跑却被当作同一组合已覆盖。
- 调整用例目标时同步 intent、TC、RA 文本与 covers。原来覆盖的目标移交到数据层或 Web 层后，显式保留缺口/移交说明。

已有客户端和断言接口可这样建立来源链（示意；basis 须先有真实可核对来源）：

```python
default_resp = _dist(api, days=30)
explicit_resp = _dist(api, days=30, stat_type="p50")
# 按同一稳定业务键取出 default_value / explicit_value 后：
expect(default_value).close_to(
    explicit_value,
    tol=confirmed_tolerance,
    basis=confirmed_basis,
    refs=[default_resp.request_id, explicit_resp.request_id],
    source="default.response.data[key].weighted_avg_cycle",
    intent="同一数据截止点下，默认参数与显式 p50 等价",
    covers="RA-01",
)
```

这条验证的是参数等价。中位数计算正确性由另一条独立原始输入复算用例承担。

## 7. 实施顺序与验收

第一批不需要新业务数据通道：修分页集合比较、非负判断、消息名基线、标题与请求不一致、非法请求拒绝后完整不变检查、清理确认，以及断言 refs/source。

第二批准备受控数据：分页 7 条、limit 不同资产不同条数、code=A/B 的未映射记录、跨小时事件、目标缺失/不同班次样本。数据准备必须在隔离环境或明确授权的环境执行，不能把本地 JSON 放进目录就假定服务也拥有这些记录。

第三批补算法验收：中位值、Tukey、trend、JPH/EMA/RSD 的独立参考计算，冻结数据截止点与口径。不可达项保留为缺口并明确目标测试层。

每批至少满足：

- 正确数据下通过，目标错误变体下相应比较确实失败；这种反例仅证明检测到该错误，不保证全部业务正确。
- 已知非空受控数据被服务错误返回为空时，不能被清洗成跳过。
- 独立数据条件确实不足时，显示阻塞/无法验证，不伪装为完成。
